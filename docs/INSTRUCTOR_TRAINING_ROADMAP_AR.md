# دليل المدرب: مسار تحديات Nuqta Workspace

**داخلي للمدرب فقط. لا ترسل هذا الملف للمتدربين ولا تضعه في مستندات عامة.**

كل الحسابات والبيانات أدناه اصطناعية ومخصصة للمحاكي المعزول. لا تستخدم هذه البيانات خارج مشروع التدريب. تم أخذ كلمات المرور من ملفات seed المحلية؛ لم أختبر تسجيل الدخول بهذه البيانات في هذه الجولة، وقد تكون كلمة مرور حساب المدرب تغيّرت إن تم تدويرها يدويًا.

## تجهيز الأدوات

1. **Browser DevTools**: ابدأ بتصفح طبيعي، ثم راجع Network وApplication/Storage لمقارنة ما يعرضه التطبيق بما يرسله ويستقبله.
2. **Burp Suite Community**: استخدم Proxy لالتقاط طلبات التطبيق، ثم Repeater لإعادة الطلب نفسه بحساب أو مؤسسة مختلفة. أرسل طلبًا واحدًا في كل مرة واحفظ ملفًا منفصلًا لكل مجموعة.
3. **AuthMatrix أو Autorize**: قارن الطلبات بين موظف ومدير ومسؤول ومستخدم من مؤسسة أخرى. لا تعتمد على نتيجة الإضافة وحدها؛ افحص البيانات الراجعة والتغيير المحفوظ.
4. **Supabase Dashboard**: للمدرب فقط، راجع سجلات الاختبار وسياسات RLS وStorage والصفوف الاصطناعية بعد كل تجربة. لا تشارك مفاتيح المشروع.
5. **ffuf**: عند تحديات اكتشاف المسارات فقط، استخدم قائمة قصيرة على المضيف المحلي `localhost:8888` وبمعدل منخفض. لا تستخدمه على أي نطاق خارجي.
6. **jwt_tool**: لفحص claims اصطناعية فقط في VULN-17؛ لا تستخدم أسرار توقيع حقيقية ولا رموزًا من خارج المحاكي.
7. **OWASP ZAP**: استخدم proxy سلبي أو فحصًا أساسيًا محدودًا على الواجهة المحلية. لا تتوقع منه اكتشاف مشاكل التفويض بين المؤسسات.

**MSF (Metasploit Framework) وHydra ليسا أداتين أساسيتين لهذا المختبر**: التحديات هنا في تفويض التطبيق وسير العمل وRLS وأدوات الذكاء الاصطناعي، وليست خدمة شبكة بها CVE. لا تشغّل تخمين كلمات مرور أو مسح شبكة. يمكن استخدام Nuclei فقط بقوالب HTTP آمنة ومراجعة على عنوان المحاكي الصريح، وليس بقوالب عامة أو فحص DNS/شبكات.

قبل التدريب، شغّل الواجهة والـAPI محليًا وتأكد من الاستجابة على `http://localhost:5173` و`http://localhost:8888/api`. حالة فحص سابق بتاريخ 2026-10-05: Nuclei موجود، بينما Burp وZAP وffuf وjwt_tool و`msfconsole` وHydra لم تكن مثبتة؛ افحص الجهاز مجددًا قبل الحصة.

## سلاسل الهجوم الأربع

1. **CHAIN-A — اكتشاف المستند**: `GET /api/v2/customers/:id` يكشف UUID مرتبطًا → استخدمه في `GET /api/v2/documents/:id` بحساب المؤسسة الثانية → أثبت أن محتوى المستند الاصطناعي نفسه ظهر.
2. **CHAIN-B — API القديم إلى تنزيل الملف**: اكتشف مرجع v1 من سجل الشبكة أو bundle → اقرأ مشروعًا أجنبيًا عبر `GET /api/v1/projects/:id` → استخرج file ID → تحقق أن `GET /api/v2/files/:id` محمي → جرّب `POST /api/v2/files/:id/download` وأثبت محتوى الملف الاصطناعي.
3. **CHAIN-C — تصعيد الدعوة**: ابدأ بدعوة اصطناعية من مؤسستك الحالية → أرسل قبولًا بدور مختلف عبر المسار الضعيف → تحقق من `organization_members` → نفّذ إجراءً تدريبيًا مسموحًا للدور الأعلى → قارن بمسار `/complete` الآمن.
4. **CHAIN-D — Mibyan إلى مستند مؤسسة أخرى**: اسأل عن المعرفة الاصطناعية المزروعة → تتبع التعليمات غير المباشرة → تحقق من طلب الأداة → سجل فشل تفويض `get_document` → أثبت ظهور محتوى المستند الأجنبي في رد المحادثة المحفوظ.

## تسجيل النتيجة وإعادة البيئة

لكل تحدٍ دوّن: الحساب والمؤسسة، الطلب الطبيعي، الطلب المعدل، الاستجابة والبيانات الاصطناعية التي ظهرت، أثر قاعدة البيانات أو Storage، المقارنة الآمنة، حدث لوحة المدرب، ثم نتيجة reset. لا تسجل `PASS` لمجرد ظهور HTTP 200.

نفّذ reset من لوحة `/instructor` → Environment بعد التجارب ذات الأثر. تحقق من الأدوار والدعوات والفواتير والمشاريع والتعليقات والمعرفة والمحادثات والجلسات والملفات وAPI keys، ثم تأكد من بقاء وصول المدرب. تم التحقق في 2026-10-05 من نجاح reset قاعدة البيانات مرتين مباشرة بعد migration الإصلاح؛ **مسار لوحة المدرب وتنظيف Storage لم يُختبرا في تلك الجولة**. راجع `docs/REAL_RANGE_VERIFICATION.md` قبل اعتبار أي تحدٍ جاهزًا أو موثقًا على أنه Verified.
