# Nuqta Workspace | Trainee Challenge Guide

Welcome to the Nuqta Workspace lab. This is a SaaS-style training application populated with synthetic users and data. Your goal is to identify unexpected behavior, collect repeatable evidence, and explain how the application should behave.

**Authorized scope:** `https://vulnerable-website.netlify.app` and the training accounts listed below only. Do not test any other domain or account.

## Training accounts

Use synthetic accounts only. These accounts let you compare users from two different organizations.

## Tools

1. **Firefox Developer Tools:** Use Network and Storage to inspect requests and responses. Firefox labels the request filter **XHR**; a separate Fetch button may not be present. Use XHR or the All filter and type a term such as `widget` in the filter box.
2. **Burp Suite Community:** Capture a request generated by normal application use, then compare it in Repeater between the two training accounts. Change one value at a time.
3. **AuthMatrix or Autorize:** Compare the same request between the two signed-in training accounts. Inspect response content, not only the status code.
4. **OWASP ZAP:** Use it as a proxy or for passive inspection within the authorized scope only.
5. **ffuf:** Use only if the instructor assigns a path-discovery exercise. Keep the list small, the request rate low, and the target within the authorized scope.
6. **Supabase Dashboard:** Instructor use only. Trainees do not need database credentials or permissions for the standard path.

Metasploit and Hydra are not needed. Do not automate password guessing, generate high traffic, or scan networks or the public internet.

## Firefox quick start

1. Open Developer Tools with <kbd>Cmd+Option+I</kbd> on macOS or <kbd>Ctrl+Shift+I</kbd> on Windows/Linux. You can also open it from the Firefox menu: **Tools → Browser Tools → Web Developer Tools**.
2. Select **Network** and reload the training page so its requests appear.
3. Select **XHR** to focus on API requests. Firefox may not show a separate **Fetch** filter; **XHR** is suitable. Choose **All** if a request is missing, then type part of its name or path (for example, <code>widget</code>) in the filter box.
4. To keep requests when navigating or reloading, enable **Persist Logs** in the Network toolbar. If the toolbar is narrow, widen Developer Tools or look in its overflow menu.
5. Select a request. Use **Headers** to inspect request and response headers, **Response** to view returned data, and **Cookies** only when needed. Do not copy cookie values, authorization headers, or tokens into notes.
6. If no request appears, clear the filter and reload the page that normally uses the feature. Do not invent or send requests to other domains.

## How to work through a challenge

1. Start in the application interface and use the feature normally.
2. Record the request and response. Repeat a request only when the challenge asks for a comparison, using the other training account or a synthetic value.
3. Check for a real effect: did a synthetic record appear, change state, or reveal content or a file?
4. Compare the result with a similar route or resource that appears protected.
5. Write a short note covering the expected behavior, observed behavior, evidence, and comparison.
6. Save evidence before moving on. Tell the instructor when a challenge changes data so the lab can be reset.

Each challenge has a collapsible **Hint** section. Read Hint 1 first and open the next hint only if needed. Challenges that use Firefox Developer Tools also include a collapsible **Firefox steps** section.

## Additional challenges: multi-step chains

After the individual challenges, choose one chain and prove it from the starting point through the final effect. Do not rely only on testing each component separately.

- **Chain A — Customer record to document:** Find information linking a business record to a document, then check the read result with the other organization's account.
- **Chain B — Older route to file:** Follow an older API reference to a project, then compare file metadata protection with download protection.
- **Chain C — Invitation to permission:** Follow invitation state and resulting membership, then prove one action allowed by that role within the same organization.
- **Chain D — Knowledge to Mibyan tool:** Follow retrieved knowledge, assistant behavior, the tool request, authorization, and the synthetic data saved in the conversation.
